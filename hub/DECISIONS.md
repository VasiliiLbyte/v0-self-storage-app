## D-001 (2026-10-29): Правила Control Hub Kit внутри репо, Claude Code работает сам

**Status:** Accepted
**Кто решил:** Василий (VasiliiLbyte)
**Контекст:** Control Hub Kit рассчитан на отдельный хаб, несколько репозиториев и цепочку
надзор → рабочий оркестратор → исполнители. У проекта один репозиторий и деплой на Vercel.
**Решение:** память проекта (рамка, журнал, решения, задачи) живёт в `hub/` этого репо.
Отдельных оркестратора и исполнителей нет: Claude Code сам пишет план, после approve оператора
делает код и проверяет его по протоколу надзора (`hub/playbook/VERIFY.md`).
Прод трогает только оператор: push и merge в `main`, SQL в Supabase, env на Vercel.
**Почему:** один репо и одна сессия проще; дисциплина kit (план до кода, проверка вместо
слов, журнал, evidence) сохраняется.
**Последствия:** нет независимой второй модели, которая перепроверяет работу. Для задач
с деньгами и RLS можно попросить отдельный `/code-review`. Задачи и журнал лежат в репо с кодом,
поэтому секреты и персональные данные в `hub/` не пишутся.
**Связано:** `AGENTS.md`, `CLAUDE.md`, `hub/playbook/PIPELINE.md`

## D-002 (2026-10-29): Миграции через `scripts/NNN_*.sql`, применяет оператор

**Status:** Accepted
**Кто решил:** фиксация сложившейся практики
**Контекст:** Supabase CLI и автоматические миграции не настроены. Схема ведётся SQL-файлами
`scripts/001…006`, их выполняют в Supabase SQL Editor.
**Решение:** каждая правка схемы, RLS, триггеров или Storage-политик — новый файл
`scripts/NNN_<суть>.sql`, идемпотентный (`IF NOT EXISTS`, `DROP POLICY IF EXISTS`,
`ON CONFLICT DO NOTHING`), с комментарием в шапке: что делает и после каких файлов.
Оператор применяет его **до** выкладки кода, который от него зависит. Старые файлы не правятся.
**Почему:** повторный запуск безопасен; порядок применения виден по номеру.
**Последствия:** фактическое состояние БД может отставать от файлов. Перед задачей с БД
сверять с оператором, что применено.
**Связано:** `hub/DEPLOY.md` §3
