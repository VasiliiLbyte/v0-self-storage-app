# Протокол самопроверки

Агент проверяет свою работу так, как проверял бы независимый надзор: верит только тому,
что запустил и увидел сам. «Должно работать» не evidence. Команда: `/verify <ID>`.

## 1. Когда

- Перед тем как сказать оператору «готово» по любой задаче
- Перед строкой DEP в «Ожидает деплоя»
- После деплоя, чтобы поставить `deployed` (`/deployed`)

## 2. Пять слоёв

Проверяется каждый слой, который задача затрагивает. Если слой пропущен, в отчёте
пишется почему.

| # | Слой | Что делать | Провал |
|---|---|---|---|
| 1 | **Код** | `git diff main...HEAD`. Прочитать изменённые файлы целиком, а не только hunks. Сверить со скоупом, «НЕ трогать» и стоп-сигналами из файла задачи | Правки вне скоупа, мёртвый код, `any`, заглушки, захардкоженные секреты и URL, `console.log` для отладки |
| 2 | **Типы и сборка** | `npx tsc --noEmit` и `npm run build` | Любая ошибка. Build типы не проверяет (`ignoreBuildErrors`), поэтому `tsc` обязателен |
| 3 | **API** | `npm run dev` и curl затронутых `app/api/**`: happy path, 400 на кривой body, 401 без сессии, 403 на чужую сущность и для не-админа | Коды или формат ответа расходятся с `API_CONTRACT.md` |
| 4 | **Живой UI** | Браузер на десктопе и на ширине 375px: сценарий из файла задачи, консоль, сеть, горизонтальный скролл | Сценарий не проходит, ошибки в консоли, вёрстка поехала |
| 5 | **Данные и безопасность** | Для задач с БД: SQL-миграция идемпотентна, RLS не даёт клиенту менять чужое и денежное. Для оплаты: сумма считается на сервере, webhook идемпотентен | Клиент может записать цену, статус или чужой `user_id`; повторный webhook меняет данные второй раз |

### Обязательные регрессии по области

| Задели | Пройти руками |
|---|---|
| `lib/supabase/*`, `middleware.ts`, `app/auth/*`, `components/header.tsx` | Логин → переход в `/dashboard` → обновление страницы → 2–3 перехода по ссылкам → пользователь всё ещё залогинен. Выход через кнопку |
| `app/booking/*`, `app/api/bookings/*`, `app/api/payments/*` | Бронь до шага оплаты: создаётся `pending`, сумма совпадает с `boxes.price_month` и скидкой |
| `app/admin/*`, `app/api/admin/*` | Не-админ получает редирект на `/` и 403 от API |
| Вёрстка | 375px и 1280px, нет горизонтального скролла |

## 3. Чеклист против файла задачи

Каждый критерий готовности из файла задачи переносится в отчёт со статусом:

| Критерий | Как проверил | Статус |
|---|---|---|
| <из плана> | <команда, файл:строка, скрин> | ✅ / ❌ / ⚠️ не проверено, потому что… |

## 4. Красные флаги

- Правки `.env*`, `next.config.mjs`, `vercel.json`, `package.json`, если их нет в скоупе
- Изменение API без обновления `API_CONTRACT.md`
- Ручная правка `content/legal/*.html` вместо `.docx` + `npm run build:legal`
- Правка уже существующего `scripts/00N_*.sql` вместо нового файла
- Service role клиент (`lib/supabase/admin.ts`) в коде, который попадает в браузер
- Сумма, скидка или статус оплаты берутся из тела запроса или из браузерного insert
- Решение опирается на то, что показывает сайт, а не на БД
- «Заодно поправил», «обновил зависимости», новая зависимость без обоснования

## 5. Итог

**Готово (verified)**, если все критерии ✅, красных флагов нет, а риски названы.
Тогда агент добавляет строку DEP-NNN в «Ожидает деплоя» и выдаёт блок деплоя
(`templates/DEPLOY_BLOCK.md`).

**Не готово**, если есть хоть один ❌: агент чинит (тот же ID с `-FIX`) и проверяет заново,
а не пишет «почти готово».

**Готово с follow-up**, если хвосты некритичны: они становятся отдельными строками
в «Следующее», а не условием готовности.

## 6. Когда просить вторую пару глаз

Для задач с деньгами, RLS и auth независимой второй модели в схеме нет (D-001).
Перед merge стоит предложить оператору `/code-review` по ветке.
